# Hello 👋

This is a living reference for how we build UI at the component, foundation, and pattern level. It documents how things should work — the when and why behind each decision — so the team can address those questions earlier in the product cycle, not after something's already been built.

## Who it's for

It's for the whole org. Designers use it most, but anyone scoping, reviewing, or giving feedback can use it to gut-check decisions — is this the right component? Has this been solved before? Is this consistent with how we do things?

## How it's structured

**Foundations** are the building blocks every UI is built from — color, typography, spacing, elevation, and iconography. These decisions underpin everything else.

**Components** are the reusable UI elements assembled from those foundations — buttons, inputs, modals, navigation, steppers, cards, and more. Each entry covers when to use it, when not to use it, how to use it correctly, known variants, and other guidelines.

**Patterns** are the recurring views and solutions to common design problems — how we handle empty states, how assignment flows are structured, how errors are surfaced, how onboarding works. Where components answer "what is this?", patterns answer "how do we solve this?"

## How to use it

We believe that early and frequent usage of the DSG from early ideation to solution validation is the best way to ensure that:

- Our product feels consistent and cohesive across all of our experiences for all our Learners, Teachers, Parents, and Admins
- Our Design, PM and Engineering teams have a shared language for talking about UI, and are aligned on how to build features
- We can focus on solving new problems instead of rehashing old ones.

### 💪🤖 Agentic usage

Your agent can easily make informed decisions and recommendations based on the guidelines via the **KA Design** Claude plugin, enabling it to review a design, screenshot, Figma frame, or live URL. The output will point you to direct references in the guidelines.

#### Enable the plugin and run the skill

1. Launch Claude Desktop
2. Open **Customize**  and navigate to **Plugins**
3. Find and enable the **KA Design** plugin
4. Now you can run the `/ka-ux-feedback` 

The plugin connects the Design Guidelines MCP for you when it's enabled, so there's nothing else to set up.

### 💪👥 Collaborative usage

This allows us to now use the design-system-guidelines powered skill in any Claude surface, including **Claude Tag** allowing the skills to be run collaboratively in Slack! Ask a Slack admin to add the Design Bundle to your channel.

## Technical details

You only need this section if you're using an agent without the KA Design plugin, or you're testing changes to the guidelines themselves.

### Connect your agent to the MCP manually

If you have the **`Claude CLI`** tool, open up Terminal and run:

```sh
claude mcp add --transport http --scope user design-guidelines https://main--6a5008743971119020a6233b.chromatic.com/mcp
```

If you have the Claude Desktop app, or another client (Cursor, etc.), add this to your MCP configuration (or ask the agent to do it for you):

```json
{
    "mcpServers": {
        "design-guidelines": {
            "type": "http",
            "url": "https://main--6a5008743971119020a6233b.chromatic.com/mcp"
        }
    }
}
```

### Hosting locally

You can host locally to test your changes to the guidelines. It will also operate faster without network latency, but make sure you have the latest version of the guidelines before you start if that's your goal.

You can run the Design Guidelines Storybook locally by going to the cloned `design-system-guidelines` repo folder and running:

```sh
pnpm start
```

Then point your agent to the local MCP endpoint:

```
http://localhost:56789/mcp
```
