# Modals - selection

<NeutralBadge label="Complex filtering" />

A secondary control center for complex or less frequent filtering needs, ensuring the primary interface remains uncluttered. Allows users to manage multiple data dimensions in a focused environment without losing the context of their current report.

## When to use

The choice to use the selection modal is determined by the need to provide access to extended filtering criteria that would otherwise overwhelm the horizontal real estate of the primary filter bar.

| Use when | Example use |
| --- | --- |
| Housing secondary filters used less frequently than primary anchors | Moving specific filter options into the modal to keep the main header clean. |
| The filtering interaction combines multiple input types that are too complex for the filter bar | Selecting a Practice type activates a previously disabled Test type dropdown below it — the modal gives dependent filters the space to reveal themselves without cluttering the filter bar. |

## When NOT to use

Avoid the selection modal when the filtering need is simple enough to be handled directly in the filter bar, or when a pre-selected default should always be visible to the user.

| Don’t use when | Recommended alternative | Rationale |
| --- | --- | --- |
| A filter needs to be pre-selected or always visible | Embedded filter dropdown | If a filter option is preselected, such as Date set to "Last 30 days," nothing pre-filtered should be hidden in the selection modal. |
| Only one additional filter is needed | Standard dropdown | If only one additional filter is needed, a simple dropdown in the filter bar is more efficient than a modal. |
| The user needs to search by keyword | Search field | Users expect search to be a persistent, high-level action in the primary UI rather than hidden in a modal. |

## States

### Default modal

All filters are secondary by default when the modal is first opened or currently applied. The modal displays all the available filter sections simultaneously.

<img src={defaultModalImg} alt="A “More filters” modal over a dimmed report showing all filter sections at once — Display options, Course, Subject, and Practice — with Reset filters and Apply filters in the footer" />

## Placement

### Common placement

Trigger the modal from a button labeled "More filters" located at the end of the primary filter bar.

The "More filters" button in the primary UI should display a numeric badge (e.g., "2") to indicate how many hidden filters are currently active.

<img src={commonPlacementImg} alt="A filter bar with Last 30 days, School, and Grade filters followed by a “More filters” button at the end" />

<img src={filterBadgeImg} alt="A filter bar where the “More filters” button carries a “2” badge, with the two active hidden filters shown as chips below" />

### Internal layout

Group filters into clearly labeled sections using headings — e.g. "Display options," "Course," "Subject." This reduces cognitive load and helps users find related filters quickly.

<img src={internalLayoutImg} alt="The selection modal with its filters grouped into labeled sections, the “Display options” section heading highlighted" />

### Footer actions

The "Reset filters" button is always in the bottom left, anchored to the footer. "Apply filters" is the primary action, bottom right. This button pair must always be visible — never buried below the fold.

<img src={footerActionsImg} alt="The selection modal footer highlighted, with Reset filters anchored bottom-left and Apply filters bottom-right" />

## Interaction

When designing the content of the modal, refer to the specific documentation for components like [dropdowns](?path=/docs/design-guidelines-components-inputs-dropdown-select--docs), [radio buttons](?path=/docs/design-guidelines-components-inputs-radio-button--docs), [checkboxes](?path=/docs/design-guidelines-components-inputs-checkbox-group--docs), and [toggles](?path=/docs/design-guidelines-components-inputs-toggle--docs) to ensure input consistency. For backdrop behavior, sizing, and animations, refer to the [Modals documentation](?path=/docs/design-guidelines-components-overlays-modals--docs).

### Applying changes

Nothing in this modal reaches the report until the user selects "Apply filters". Every control — dropdowns, checkboxes, toggles — holds its pending value inside the modal until then, so the user can set several filters at once without the report re-querying between each one.

Dismissing the modal with the X, the Escape key, or a click on the overlay discards pending changes and leaves the report unchanged. Filters are non-destructive and quick to redo, so dismissal does not warn — unlike a functional task modal, which must warn before discarding entered data.

Reopening the modal shows the filters currently applied to the report, not the pending state that was abandoned.

### Layout — category labels

Category labels sit to the left to provide an anchor point for the filter controls, creating a clear label column on the left and filter controls on the right.

<img src={categoryLabelsImg} alt="The selection modal with a highlighted left column of category labels aligned against the filter controls on the right" />

### Toggle behavior

Within the modal, toggles should be placed full-width and left-aligned, with the label on the left and the toggle aligned to the right.

<img src={toggleBehaviorImg} alt="A “Display options” section with full-width toggle rows, each label on the left and its toggle aligned to the right" />

### Dynamic content — adaptive controls

Dropdowns transform into exposed checkboxes when the available options drop to five or fewer, following the [option-count rule](?path=/docs/design-guidelines-components-inputs-checkbox-group--docs) used across the system. Five is the trigger rather than the wider six-to-eight band, because that band calls for a judgment about the content — one that can’t be re-made at runtime. A single fixed threshold keeps the transformation predictable instead of flipping as the user filters.

<img src={adaptiveControlsImg} alt="Before and after: a Course dropdown collapses into a short set of exposed checkboxes (Algebra 1, Geometry, Algebra 2, Trigonometry) once the option list is reduced" />

### Dynamic content — parent/child logic

Support hierarchies that filter one option based on a parent selection — e.g. selecting a "Practice" enables a "Test" dropdown.

When a parent selection changes, the child keeps its value if that value is still available under the new parent, and is cleared if it is not. Never carry forward a child selection the user can no longer see — an orphaned value produces a filter state nothing in the interface explains. Where the new parent has no children, the child control returns to its disabled state.

The clearing happens in the modal, visibly, at the moment the parent changes — not silently on Apply.

<img src={parentChildImg} alt="A Practice dropdown set to “Placements” enabling a dependent “Select a test” dropdown below it, both highlighted" />

### Reset filters behavior

Selecting "Reset filters" returns every control in the modal to its default value — dropdowns, checkboxes, and any toggles set within the modal. It resets to defaults rather than clearing to empty: a toggle that ships on returns to on, not off.

The modal stays open and nothing reaches the report until the user selects "Apply filters". Reset is a change like any other made here, so it follows the same commit path — the user can see what the reset did, adjust from there, and dismiss without committing if they change their mind.

This is not the same action as Clear filters in the filter bar, which removes active filters from the report rather than returning controls to their defaults. Clear and reset are distinct verbs in this system: clear removes to empty, reset returns to a default. See [Clear filter](?path=/docs/design-guidelines-components-inputs-clear-filter--docs).
