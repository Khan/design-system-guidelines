# Collecting feedback

When a user wants to tell us something about our platform, they should be able to do it in-context, where they are, and the process should be quick, familiar.

## Usage and purpose

There are two main variants of the feedback widget, each with its own affordance and use case.

### "Sentiment" variant

<img src={triggerOpinionImg} alt="Feedback trigger for opinion variant" />

Choose **sentiment** when there is one identifiable item the user just consumed. Not only is the positive/negative signal valuable–this modality also allows us to present more relevant feedback types specific to the item type and sentiment.

Logged:

- sentiment
- type
- comment
- item ID

### "General" variant

<img src={triggerGeneralImg} alt="View cropped to show the Teacher navbar with the 'Leave Feedback' button above the profile link" />

Choose **general** when the subject is a surface or workflow rather than a single item.

The Teacher navbar example above allows the teacher to provide feedback on anything they can view in this layout (i.e. any non-modal experience). While there should be a default set of types, consider whether a specific view, e.g. a teacher report, would benefit from more targeted types.

The event data will be sentiment, type, and comment, tied to that item

### Get that feedback

<img src={triggerOpenImg} alt="Feedback widget open, showing the open widget popover" />

All variants open a popover like the one above, with various labels/titles being customizable. One of the biggest levers is in naming the "feedback types." 

## Choosing feedback types

1. **Write for the user's moment** The list should hold what a user could plausibly want to say at that point, on that surface.
2. **Serve the user's needs before the team's questions.** A type that exists because someone wants to measure it, and/or that's phrased in words no user would reach for, adds noise. A user should recognize their own reaction in the list at a glance.
3. **Up to 5 options + "Other"** If the list isn't quickly scannable, users may exit, or just pick "Other". Don't get in the way of their actual task. Fewer is better!
4. **Positive and negative are separate lists, and may have overlap.** A dimension that can be done well or badly ("Tone", "Pacing") could appear in both, with the sentiment and notes carrying the verdict.

## Copy

You can customize the prompt, the title (or specific negative and positive sentiment titles), the thumbs-down title, an optional subtitle, the sentiment group label, and every type label.

For titles and body copy, follow the <a href="/?path=/docs/design-guidelines-components-overlays-modals--docs#copy">Modal copy guidelines</a>

Generally, the goal is match the user's intent here, so think from their perspective. This is especially important for type labels, which should be 1-3 words and non-technical.

## Widget popover placement

The feedback popover should be anchored to the affordance that opened it, opening toward empty space or chrome — away from the region the feedback responding to. This enables sighted users to reference any helpful details. 

The popover is a fixed `425px` wide and the height is dynamic.

## Responding to input

- A tapped thumb fills, so the response stays visible. That sentiment also determines the title and feedback types to present.
- **Sentiment:** the thumbs are replaced by a thanks message, which takes focus on close. One submission per item — an item gets one verdict.
- **General:** the popover swaps to a thank-you pane and the launch signifier stays available for another submission*.*
- The user must actively close the widget. Clicking outside the widget bounds will not dismiss it. If it did, the user could lose their work if they attempt to scroll or otherwise view the content they want to leave feedback on. Users likely will give up potentially losing important feedback.

## Custom implementation

Use the customizable fields. 

Customizations should be rare. One example is feedback on video content, where we silently include the current timestamp of the video player as a signal.

If other data needs to be captured or represented, reach out to the Design Infra team.
