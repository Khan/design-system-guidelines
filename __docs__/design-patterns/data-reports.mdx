# Data reports

This guide covers how to build a data report: what to show, how to lay it out, and how to handle empty and error states. It applies to every data visualization component.

<a href="./?path=/docs/design-guidelines-foundations-data-visualization--docs">Data visualization</a> holds the rules every chart follows: chart types, anatomy, color, number formatting, and writing. This page applies them to whole reports.

## Usage and purpose

| Component | Answers | Use case and purpose |
| --- | --- | --- |
| <a href="./?path=/docs/design-guidelines-components-data-visualization-summary-cards--docs">Summary cards</a> | What's the headline? | Shows key numbers in words and digits, with no chart to decode. Stat cards show one metric. |
| <a href="./?path=/docs/design-guidelines-components-data-visualization-progress-charts--docs">Progress charts</a> | How close are we to the goal? | Shows a current value against a goal, like a class challenge or grade level target. |
| <a href="./?path=/docs/design-guidelines-components-data-visualization-distribution-charts--docs">Distribution charts</a> | How is the group spread out? | Shows how many students, classes, or schools land in each range, like assignments completed, or how that spread changed between two periods. |
| <a href="./?path=/docs/design-guidelines-components-data-visualization-trend-charts--docs">Trend charts</a> | How has it changed? | Shows a value across three or more periods, like growth across units. |
| <a href="./?path=/docs/design-guidelines-components-data-visualization-data-tables--docs">Data tables</a> | Who exactly, and what do I do? | Lists each individual or item with exact values, so readers can find and act on them. |
| Heat map (coming soon) | Where are the patterns? | Shows a value across two dimensions, like mastery by student and skill. |

## Making a useful chart

A chart earns its place only when it answers the question faster than a number or a table would.

### Number, chart, or table

| Use | When | Example |
| --- | --- | --- |
| A number, in a <a href="./?path=/docs/design-guidelines-components-data-visualization-summary-cards--docs">summary card</a> | The takeaway is one value | 11,033 students assessed |
| A chart | Readers need to see a pattern, a change, or a gap | Scores climbed 133 points since the last assessment |
| A <a href="./?path=/docs/design-guidelines-components-data-visualization-data-tables--docs">data table</a> | Readers need exact values, or need to find and act on individuals | Each student's score, with flags |

### What makes a chart useful

<ul>
    <li><Do /> Answer one question per chart, and state the answer in the title: "Scores climbed 133 points since the last assessment," not "Average score."</li>
    <li><Do /> Show only the data the title needs. Move the rest to a table or another chart.</li>
    <li><Dont /> Chart a single value. Use a summary card.</li>
    <li><Dont /> Make readers match many colors to a legend. Past four series, fold the rest into "Other" or use a table.</li>
    <li><Dont /> Show more dimensions than one chart can show clearly. Split it into two charts, or use a table.</li>
</ul>

## Showing growth

Growth compares the same students across two or more assessments, like middle of year and end of year.

| To show | Use |
| --- | --- |
| How the split by level changed between two periods | <a href="./?path=/docs/design-guidelines-components-data-visualization-distribution-charts--docs#comparing-periods">Distribution chart, comparing periods</a> |
| A value across three or more periods | <a href="./?path=/docs/design-guidelines-components-data-visualization-trend-charts--docs">Trend chart</a> |
| Which students moved, and by how much | <a href="./?path=/docs/design-guidelines-components-data-visualization-data-tables--docs#table-with-summary-tabs">Data table with summary tabs</a>: Moved up, Same level, Moved down |

<ul>
    <li><Do /> Say who's included: "29 students took both." Leave out students without both results, and say how many: "4 didn't take the middle of year assessment."</li>
    <li><Do /> Lead with level movement, then points: "8 of 29 students moved up a level." A point change needs context to mean something, and a level doesn't.</li>
    <li><Do /> Show a change within a level, so a gain isn't hidden: "Approaching, no change" with "↑ 10 pts."</li>
    <li><Do /> Sort students by change by default, so the biggest moves in both directions are easy to find.</li>
    <li><Dont /> Show only an average. An average can go up while some students go down.</li>
</ul>

## Layouts

Data appears in one of two layouts, and each has its own rules.

| Layout | Use when | Controls |
| --- | --- | --- |
| Container | One chart that needs a few controls, or none | Inside the container, top right |
| Own page or section | The data needs more controls than fit beside the H3 | Above the data |

## Page order

Reports read top to bottom, from overview to detail.

| Order | Content | Controls |
| --- | --- | --- |
| 1 | Summary stats, like a row of stat cards | None |
| 2 | Containers | Inside each container |
| 3 | Own section, like a full table | Filter bar above the data |

Data with its own section always goes at the **bottom** of the page. Never place it above containers or between them.

### Control scope

Controls only change the data they sit with, never data above them.

- **Container controls** change only that container.
- **Filter bar controls** change only the data below them in that section.
- **Never place a filter bar above containers.** Containers always sit higher on the page, so a filter bar can never affect a container.

## Containers

A container holds one chart with its section heading, title, and controls. For its anatomy, headings, and controls, see <a href="./?path=/docs/design-guidelines-components-data-visualization-chart-container--docs">Chart container</a>.

## Own page or section

### When data needs its own page or section

A container has outgrown inline controls when the data needs:

- More than about three controls.
- Any control that opens a multi-field popover.

This is usually a sign the data needs its own page or a significant section of a page.

### Page and section controls

Controls sit outside and above the data, not inside a container. See <a href="./?path=/docs/design-guidelines-patterns-filter-and-sort--docs">Filter and sort</a> for filter bar guidance.

## States

### Empty states

An empty state's copy depends on why the data is missing. Its placement depends on the layout. Name what's missing, say when data will appear or what to do, and offer an action only when the user can fix it from there.

| Layout | Show | Action |
| --- | --- | --- |
| One container is empty; others have data | An empty state inside that container | Secondary button, only if the fix happens here |
| Every container would be empty for the same reason | One empty state in place of all containers | One primary button |
| Own page or section | An empty state in place of the data, below the controls | One primary button, only if the fix happens here |

Any layout can be empty because of its filters. See [Filtered to nothing](#filtered-to-nothing).

Every data report empty state uses the **No report data** spot illustration, in every layout and for every cause. The illustration is decorative; the headline and body carry the meaning.

#### Empty container

- Keep the H2 so readers still know what the section is. The empty state replaces the H3 and the chart.
- Write copy specific to that container: "No growth data yet," not "No report data yet."
- Keep only controls that could change the result, like a date filter. Hide the view toggle and download.
- Leave out the button when the fix happens somewhere else, like students finishing a test.

#### Empty page or section

- Keep the page or section title and description.
- Keep controls that could change the result, like search and filters. Hide controls that act on data, like download.
- The empty state replaces the table or chart, directly below the controls.

#### Filtered to nothing

This applies to containers and to pages or sections.

- Keep the controls that caused the empty result visible, so users can see and change them.
- In a page or section, offer "Clear filters" as a secondary button. See <a href="./?path=/docs/design-guidelines-patterns-filter-and-sort--docs">Filter and sort</a>.
- In a container, point to the control instead: "Try a different date range." Skip the button; the control is right there.

### Empty state copy

| Part | Rule | Example |
| --- | --- | --- |
| Headline | Name what's missing. Sentence case, no period. Use "yet" when data is coming. | No growth data yet |
| Body | One sentence: why it's empty, or when data will appear. End with a period. | Add students to your class to start tracking their progress. |
| Button | Verb first, 1–3 words. Only when the user can fix it here. | Add students |

Use "yet" to tell teachers nothing is broken; the data is on its way. Cut filler like "available" and "begin."

| Cause | Headline | Body | Action |
| --- | --- | --- | --- |
| Not set up | No report data yet | Add students to your class to start tracking their progress. | Add students |
| Waiting on activity | No activity yet | Data shows here once students start practicing. | None |
| Filtered to nothing | No results for these filters | Try a different date range or clear your filters. | Clear filters (page or section only) |
| Not enough data | Not enough data yet | Check back after students complete more skills. | None |

### Error

An error state means data failed to load. It's never the user's fault, so the copy says what happened and offers a way to try again.

#### Full page errors

A full page error affects the whole page or section. What to show depends on whether any data loaded.

| Situation | Show | Action |
| --- | --- | --- |
| Nothing loaded | An error state in place of the data, below the controls | Primary "Try again" button |
| Earlier data loaded, but the update failed | **One** banner at the top of the content area, above the controls. Keep the earlier data. | "Try again" link in the banner |

- Keep the page title, description, and controls.
- Use one error for the page, not one per container.
- Never hide data that already loaded. Say when it's from.
- Make sure screen readers announce the error when it appears.

#### Container errors

When one container's data fails to load, show the error inside that container. The rest of the page still works.

- Keep the H2 and the container's controls.
- Use the error spot illustration, not No report data. An empty state says data is on its way; an error says something broke.
- Offer a secondary "Try again" button.
- Make sure screen readers announce the error when it appears.

#### Error copy

Say what happened, then offer a way to try again. Don't blame the user. Don't show error codes, technical messages, "Error:" prefixes, "Oops," or "please."

| Situation | Message | Action |
| --- | --- | --- |
| Container couldn't load | Headline: Couldn't load growth data<br />Body: Something went wrong on our end. Try again in a moment. | Try again |
| Page couldn't load | Headline: Couldn't load this report<br />Body: Something went wrong on our end. Try again in a moment. | Try again |
| Page couldn't update | Couldn't update. Showing data from 9:15 AM. | Try again |
