# Borders and dividers

Borders define edges; dividers separate elements. Together with <a href="./?path=/docs/design-guidelines-foundations-spacing--docs">Spacing</a>, they enable users to perceive how elements are grouped hierarchically.

## Principles

    <Principle
        label="Graduated"
        title="Use the lightest tool that works"
        description="Spacing, then lines, then borders — each step up adds more visual weight. Only reach for the heavier tool when the lighter one isn't enough."

## Borders

A border makes an edge explicit — it says this is where something begins or ends. Use a border when that boundary carries meaning: when what's inside behaves differently from what's outside.

The system has two neutral border colors, ordered by contrast. Weight stays constant at `border.width.thin` (1px); only the color token changes. A thicker border (`border.width.medium`, 2px) is only ever used for hover and focus states.

| Color | Token |
| --- | --- |
| Subtle | `semanticColor.core.border.neutral.subtle` |
| Default | `semanticColor.core.border.neutral.default` |

<img src={borderColorsImg} alt="Two rounded squares showing the Subtle and Default border colors, from lower to higher contrast" />

### Subtle border

Subtle border doesn't meet 3:1 contrast on its own — and doesn't need to when the border isn't essential for identifying the component or understanding its state. The test: if the border disappeared, would the interface still make sense? If so, Subtle works, because other cues like a text label, surface color, elevation, or an icon already identify the element. If the border is the only thing showing where an interactive element is, use Default.

Use for: cards, panels, dropdown menus, neutral buttons, dynamic action buttons, etc.

### Default border

Used when the border is the primary signal — the main thing telling the user an edge exists and that the element is interactive. Default meets the 3:1 contrast threshold needed to be perceivable on its own, without relying on elevation, shape, or other supporting cues.

Use for: form inputs, selects, and textareas on flat surfaces where the border alone defines the interactive target.

<Figure
    src={defaultBorderImg}
    alt="Mockup highlighting a text input whose edge is defined by a default-color border"
    caption="The text input uses a default border to meet contrast requirements — ensuring the field edge is perceivable for all users."
/>

### Focus border

Applied when an element receives focus — either through keyboard navigation or on initial click.

Use for: all interactive elements when focused — buttons, inputs, links, checkboxes, selects. Always high-contrast. Never suppressed.

Do not set focus states manually using borders. Instead, use the [focus package](https://khan.github.io/wonder-blocks/?path=/docs/packages-styles-focus-styles--docs#when-to-use&globals=pseudo.focusVisible:!true) offered in Wonder Blocks to apply a consistent focus treatment.

<Figure
    src={focusBorderImg}
    alt="Mockup of a dropdown in focus, surrounded by a blue outer ring"
    caption="The focused dropdown shows the blue outer ring — making clear which element is in focus without changing its size or position."
/>

### State borders

Border color changes to communicate interactive state. The shape and weight remain constant; only the color token changes: selected and focus use `semanticColor.core.border.instructive.default`, error uses `semanticColor.core.border.critical.default`, and disabled uses `semanticColor.core.border.disabled.strong`.

Use for: selected, active, error, and disabled states on form inputs and interactive components.

## Dividers

A divider is a 1px hairline in `semanticColor.core.border.neutral.subtle` that marks a boundary between elements. Dividers work in four specific contexts:

- To separate table cells
- To separate headers and footers from their associated content
- To divide a container into sections
- To separate the items of a searchable list

Use a divider when adjacent regions behave differently — a fixed header above scrolling content, or list rows that are each their own target. When regions behave the same — like groups of form fields under their own headings — the job is grouping and hierarchy, and spacing and headings are usually enough. Add a divider only when spacing can't do the job alone: dense content like data tables, where more space would cost too much, or groups that need to read as distinct at a glance.

### Table dividers

Row lines separate data in tables. They're the default separation strategy — low visual weight, clear enough for most data densities. Apply one strategy consistently per table.

Use for: separating rows in data tables. Don't mix row lines with alternating rows or a full grid within the same table.

<img src={tableDividersImg} alt="Data table with horizontal row lines separating each row of content" />

### Header and footer dividers

Marks the boundary between a fixed element — like a header or footer — and the content it contains.

Use for: the bottom edge of modal headers, the top edge of modal footers, and sticky navigation bars where a boundary between the fixed element and scrolling content is needed.

<img src={headerFooterDividersImg} alt="Modal dialog with lines separating the header and footer from its scrolling content" />

### Section dividers

Used to communicate the grouping of content within a component or pattern.

Use for: separating labeled filter groups within a panel or modal, and dividing distinct content blocks within a single surface. Skip the line directly below an in-content heading that already introduces what follows — that's different from a header divider, which marks a fixed-to-scrolling boundary regardless of whether the header has a heading.

<img src={sectionDividersImg} alt="Modal with lines separating distinct blocks of form content into groups" />

## Choosing between borders and lines

Choose by where the list sits and what it's for, not how many items it has. Two tests decide it: if the list has a search or filter control, or if it already sits inside a container — like the content card in a Job layout — use line dividers.

| Use bordered cells when | Use line dividers when |
| --- | --- |
| The set is short and fixed, and the user picks one | The user scans or searches the list |
| There is no search or filter control | A search or filter control is present |
| Options sit directly on the page background | The list sits inside a container |

### Bordered cells

Use bordered cells for a short, fixed set of options where the user picks one — like choosing which class to enter. The options sit directly on the page background, so each one needs its own border to define its edge. The gap and border around each option make every choice stand out on its own.

<Figure

    caption="Bordered cells work here because the list is short, has no search, and sits directly on the page background — each class needs its own edge. The selected state uses the focus border color with a filled radio button to confirm the choice."
/>

### Line dividers

Use line dividers for lists the user scans or searches — like a course catalog or a filtered set of results. These lists usually sit inside a container, such as the content card in a Job layout, which already defines the edge. One outer border with hairlines between rows stays light, and it's still the right choice when a filter narrows the list to just a few items.

## Accessibility

### Focus rings must meet contrast requirements

The focus ring must have a contrast ratio of at least 3:1 against adjacent colors. This applies in both light and dark mode. Do not use low-contrast or thin focus styles; users who rely on keyboard navigation need prominent focus markers.

### Borders must not be the only signal for error states

Color alone is not sufficient to communicate state, because users with color vision deficiencies might not perceive it. A red border on an error field must be accompanied by an error message, an icon, or another non-color indicator.

### Ensure dividers are not mistaken for interactive elements

A horizontal rule should not be styled in a way that could be confused with a button, link, or selectable row. Keep lines visually subdued and consistent with their role as structural separators.
